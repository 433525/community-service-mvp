- **演练身份**：`visitor` / `member` / `reviewer` 三种本机模拟身份（`types.ts:28-30`），不是真实账号或权限。
- **合成数据**：全部作者、社区、帖子、留言、举报、审核与订单事件均为虚构，只存在当前浏览器。

## 2. 状态转换矩阵

### 2.0 共同守卫与副作用约定

所有写操作都走同一持久化包装 `persistState`（`store.ts:668-731`）：先检查"损坏存档恢复态"，再检查跨标签 `conflict`，序列化超过上限或写入失败则本次不应用并回滚，成功后才更新内存状态并写 `localStorage`。业务动作的守卫顺序通常是：

1. `blockedByRecovery()`（`store.ts:787-791`）——存档恢复态禁止写入；
2. 角色守卫 `requireMember()`（`store.ts:933-940`）或 `requireReviewer()`（`store.ts:942-946`）；
3. 业务条件（目标存在、可见性、状态、理由、长度、数量上限等）。

副作用分三类，互不替代：

- **审核日志 `auditLog`**：只由 `moderate-post`、`moderate-comment`、`resolve-report`、`hide-message` 四类动作写入（`types.ts:40-45`；`store.ts:948-963`）。**订单履约动作不写审核日志**。
- **订单事件 `Post.orderEvents`**：由订单动作追加（如 `store.ts:1201-1205,1265-1272`），最多 100 条（`store.ts:79,227-238`），是订单状态的唯一时间线。
- **系统通知线程**：`appendSystemNotice`（`store.ts:817-858`）向 `kind === 'system'` 线程追加本机通知。触发点：本人内容审核结果（`store.ts:1715-1717,1773-1775`）、合成对方接单（`:1240-1243`）、合成对方申请完成（`:1308-1311`）、合成对方确认完成（`:1393-1396`）、本人订单留言被下架（`:1957-1959`）。
- **时长账本**：仅订单完成时追加一条 `unsettled` 记录（`store.ts:905-921`，调用点 `:1345,1391`）；账本达上限则跳过并在提示中说明。

## 3. 角色能力表

### 3.1 身份与校验机制

- 演练身份保存在 store 的 `membership` ref，初值 `visitor`，**只在内存中切换，不写入存档**（`store.ts:629-630`），刷新后回访客。
- `setMembership` 只校验枚举值，不校验操作者身份（`store.ts:923-931`）；任何身份都可切换。
- 业务动作先过存档恢复态，再过分角色守卫：`requireMember`（`store.ts:933-940`）与 `requireReviewer`（`store.ts:942-946`）。
- UI 层另设整页拦截：`App.vue:114-116`——审核 tab 优先渲染 `ModerationView`（页内再按身份拦截）；访客与审核员打开其余五栏时只显示空状态文案，不渲染页面正文。
- **UI 隐藏与 store 守卫都不等于服务端权限**：本机存档、身份选择器与 Pinia store 都可被本机用户绕过或直接修改。

### 3.3 订单履约动作的"本机角色"（在 member 身份内）

订单动作全部要求 `member` 身份（visitor/reviewer 一律拒绝），但在成员内部还按"本机参与者角色"细分（`store.ts:860-865`）：

注意：两种"代合成对方"按钮只是补齐单机双人流程的演练入口，产生的订单事件明确标注 `synthetic-counterpart`（`types.ts:107-124`；`store.ts:1235-1243,1301-1311,1384-1396`），页面注明"对方是合成演练对象，不会收到任何通知"（`PostCard.vue:216`；`types.ts:341-342`）。**这不等于真实双方确认或真实履约。**

### 3.4 角色边界小结

1. 审核员不能代替成员发布/评论/接单/报名/留言/举报；成员不能审核/处理举报/下架。
2. 访客看不到社区正文，且所有写动作被角色守卫拒绝；审核 tab 对访客可见但页内仍拦截。
3. 审核员打开五栏页面时只看到"审核员工作入口"空状态，不能浏览社区正文；审核页的内容管理仍会展示帖子/评论原文与留言。
4. 所有角色都没有真实身份核验；切换身份只是本机演示。
5. 订单动作的"作者/接单成员/合成对方"是数据关系与本机按钮的区分，不是第四种账号角色。

### 4.4 已知缺口与建议下一步

1. **审核可逆/复审没有界面策略**：store 接受任意 `REVIEW_STATUSES` 且只排除同状态（`store.ts:1673-1778`），但审核页没有 `rejected/hidden → approved` 或 `approved → rejected` 的恢复/复审入口（`ModerationView.vue:37,43,53,54`），提交者也没有重提/申诉路径。建议先确定"是否允许恢复/重审、由谁操作、写什么理由与日志"，再决定是否加界面，避免共享层与界面规则长期不一致。
2. **举报模型缺少举报人字段与去重**：`Report` 只有目标、理由、状态、处理说明（`types.ts:243-252`），"我的举报"实际展示本机全部举报（`MessagesView.vue:84`）；`reportContent` 未检查同一目标是否已被举报（`store.ts:1780-1865`），且创建举报不写审核日志（`:1856-1864`）。建议先确定本机是否模拟多成员语境，再决定加 `reporterId`、去重规则，或至少调整"我的举报"文案与标题。
3. **订单履约是单机"代合成对方"演示**：完成/取消/争议流程齐全（`store.ts:1248-1528`），但"双方确认"由同一本机成员通过明确标注的按钮代合成对方完成（`PostCard.vue:227-234`；`types.ts:107-124`），订单事件标注 `synthetic-counterpart`，没有真实对方、通知或结算。文档、演示与汇报都必须写成"本机演练"，不能写成真实完成或真实双方确认；账本必须保持 `unsettled`（`types.ts:144-146`；`store.ts:905-921`）。
4. **订单动作不写审核日志**：审核日志只覆盖审核、举报处理、留言下架（`types.ts:40-45`）；订单状态变化只写 `Post.orderEvents`（如 `store.ts:1201-1205`）。两套记录口径不同。若后续运营需要审计订单处置，建议明确是否统一写入 `auditLog`，或在文档中说明订单时间线即订单审计来源。
5. **已取消订单在消息页不可见**：消息页订单列表只包含 accepted/completion-requested/disputed/completed（`MessagesView.vue:13-26`），不含 `cancelled-local-demo`；只读提示里的"已关闭"分支（`:33-38`）实际不可达。已取消订单仍出现在"我的 → 服务记录"（`ProfileView.vue:24-27,235`）。建议统一两处口径，避免用户找不到刚关闭的订单。
6. **争议恢复状态单一**：`resolveOrderDispute(resume)` 不论争议从哪一步发起，一律回到 `accepted-local-demo`（`store.ts:1508`）；若从 `completion-requested` 发起争议，撤销后原完成申请不会恢复，需要重新申请。建议在界面/文档说明，或按争议来源恢复状态。
7. **B 端反馈/投诉无界面**：`addComplaint` 无调用方，`complaints` 不渲染；我的页底部"有想反馈的内容吗？"只跳消息页（`ProfileView.vue:262`）。建议实现最小反馈入口，或调整文案避免暗示已经可以提交反馈。
8. **旧存档活动缺少 `volunteerKind` 时无法报名**：`signUpForEvent` 现在要求活动招募（`store.ts:1530-1542`），旧记录缺少类型标识会被拒绝并提示"重新发布活动"。这是一致性修复后的兼容结果，建议在演示说明中列出，避免把提示当成故障。
9. **身份与存档不是安全边界**：`membership` 不持久、可任意切换（`store.ts:629-630,923-931`）；UI 隐藏与 store 守卫都不能阻止直接改本机存档。生产版必须逐请求服务端校验；演示中不得把身份选择器当权限。
10. **A+ 桥文案与读取范围需要 A+ 负责人复核**：A+ 读取器现在包含全部求助订单状态（`community-bridge.ts:81,95-97`，A+ 界面显示社区状态 `src/App.vue:50-51,1454`），但 A+ 弹窗描述仍写"只登记'求助 / 开放'的合成帖子"（`src/App.vue:1408`）。这属于 A+ 界面文案，不在本文件 B 五栏范围，建议 A+ 负责人核对后再统一表述。
