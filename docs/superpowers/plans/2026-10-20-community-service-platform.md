# 社区服务平台分档与实施计划

- 日期：2026-10-20
- 权威功能基线：《社区服务小程序功能说明.docx》（正文及参考图）。附件说明完整产品愿景，不构成真实服务授权、居民数据处理许可、对外联系授权或上线批准。
- 目标：实际运营；评估 Coalesce 是否适合复用，并参考 TimeOverflow 业务流程；使用 DeepSeek 复核去敏计划；代码存放于项目专用私有 Git。
- 当前交付决定：A+本地合成数据 MVP 已实现，前端采用 Vue 3 + Vite + Vant；记录保存于当前浏览器 `localStorage`，支持 JSON 全量导入/导出；不接 API、数据库、真实数据或真实渠道。本机明文存储和手动备份不构成生产级权限、备份或运维能力。服务类型暂不定，MVP只用“待判定/未分类”。当前路线为：G0运营发现 → A+生产工具选型/配置及合成环境验收 → G1与G2分别通过 → G3书面批准限定范围的 A+真实人工收件试点 → 试点复盘 → 单独决定是否立项 B1软件开发。G3不授权 B1履约或 B5紧急调度；B1开发获批后，真实履约上线仍需独立批准。
- 功能与准入：A+登记只代表进入分诊流程，不自动发布到任务大厅或开放接单。附件要求求助订单发布前必须实名认证，且订单进入任务接单大厅；这与 A+登记是两条独立流程。附件提到的服务类型是需求和评估对象；每一类真实履约必须由有权运营方单独批准。
- Git 目标：代码后续存放于项目专用私有 Git；本轮按用户指示跳过 Git 操作。

## 一、建议结论

按附件规划完整产品：首页、社区、发布、消息、我的，以及实际运营所需后台。先验证 A+登记/分诊的运营流程并完成有限真实收件试点及复盘，再单独决定是否开发 B1履约；之后逐步评估内容互动、账户兑换和高风险服务。

**A+ 是通用登记入口加内部分诊队列。**入口可由居民填写，也可由工作人员代录；开放范围、渠道和字段由 G0 决定。新登记先进入“待判定/未分类”队列，由获授权人员分诊，先用合成数据演练。A+不含公开任务大厅、志愿者接单/履约、社区互动、用户私聊、时间账户/兑换或平台应急调度。A+通用登记不绕过求助订单实名门槛；真实居民信息启用前须通过字段/留存、权限/审计、值守和适用治理闸门审批。

**B 承接附件的完整产品愿景。**附件中的求助、志愿者、社区动态、活动、消息、证明、时长和兑换等需求保留在路线图，不因 A+先行而删除。实际履约、敏感数据、用户互动、位置和账户能力依各自治理闸门逐项开放。

目前的公开页面初筛尚未找到已被证实适合作为 A+ 或完整 B 的底座；这只是待验证假设，不代表候选项目都已被源码排除。TimeOverflow 用于组织角色、供需发布、匹配/接单、服务确认、记账与线下承接流程参照；Coalesce可在需求确认后对 B1任务大厅和B2活动/志愿者管理分别做 fit-gap，但目前没有证据证明其满足实名求助订单任务流；CiviCase 的个案/活动记录模型可参考。定制开发前先做受控表单/工单、合规 SaaS/低代码和开源候选的配置方案比较，候选覆盖、维护、数据控制或许可证不达标时再以证据说明自建理由。

## 二、治理闸门与风险分档

### 治理闸门 G

| 闸门 | 范围 | 通过证据 |
|---|---|---|
| G0 运营发现 | 确认组织与试点社区、目标人群、受理渠道、角色、供需、值守、流程、字段用途、数据责任角色、签署人和试点指标 | 有权负责人签署发现与授权记录；记录数据责任角色（由运营/专业人员确认）、范围、流程、字段草案、指标、未决项负责人及期限 |
| G1 主体与保护 | 分别确认 A+登记/分诊边界和 B服务逐类准入/拒绝、人员核验、服务边界、对象保护、投诉复核及转介责任 | 有权主体批准；A+范围、B服务准入矩阵、投诉/申诉/事故/停单规则分别形成书面记录 |
| G2 人员/流程/系统 | 值守与替班、培训、同意/撤回、纠错、数据留存、权限审计、备份恢复和事故演练 | SOP及演练记录；正式环境与开发数据隔离；系统控制经运营/数据负责人验收 |
| G3 有限试点授权 | 仅授权限定范围的 A+真实人工收件试点：社区、人群、登记范围、人员、时段、容量、A+指标、成功/停止阈值和复核日 | 有权运营负责人书面批准；超范围登记被阻断，达到停止条件暂停新增；不授权 B1履约或 B5平台紧急调度 |

G0–G3 是处理真实业务的门槛，不阻止使用合成数据完成原型和验收。产品开发完成不能替代运营批准。

### 服务风险 R

- R0：一般信息展示。
- R1：低接触的基础互动或普通社区信息。
- R2：个人联系、位置、财物、上门或开放互动风险。
- R3：儿童、医疗、紧急响应或可能造成严重伤害的场景。

数据敏感度 D 单独分级：D0公开信息，D1基础账户/联系方式，D2精确位置、照片、行动能力/健康备注及个案资料，D3儿童、医疗或紧急情况细节。R与D分别记录、按较严格的治理要求控制；D2/D3默认不进入公开页面或普通志愿者视图。

风险取决于实际服务方式、对象、环境和信息处理，不由名称决定。附件中的陪诊、接送孩子、紧急求助、家政/维修等按具体做法评审；风险未评审或责任人未签署时，能力保持关闭。紧急静态渠道信息不等同于平台全天候响应或调度。

### R×G 放行矩阵

G0 是所有阶段的共同发现与授权记录；下表说明真实数据/履约的最低治理检查点。高风险组合按更严格一档处理。R3 的保护措施由运营方结合服务场景、属地主管要求和专业意见书面确定，不把某一种控制（例如双人服务）误写成普遍法律要求。

| 风险 | G1 主体与保护 | G2 人员/流程/系统 | G3 有限试点 |
|---|---|---|---|
| R0 信息展示 | 内容责任人与来源核验 | 发布/撤回权限和更正方式 | 指定社区、内容范围、复核日 |
| R1 低接触服务或普通互动 | 类别边界、投诉和退出路径 | 角色、最少字段、通知失败/人工接手流程 | 人员、时段、容量及成功/停止阈值 |
| R2 联系/位置/财物/上门等 | 按具体暴露面分别评审对象、人员、交接、投诉和保护措施 | 精度/可见范围、授权记录、访问审计、替班、事故及删除/留存流程 | 明确白名单、地理/时间/容量限制，演练后签署 |
| R3 儿童/医疗/紧急或可能造成严重伤害 | 专项保护与转介方案、责任人及专业复核；无明确责任方案即不开放 | 限定人员、访问面、值守/备援和事故响应；控制按场景评审 | 单独书面批准并限定人群、类别、时段、容量和复核日；未满足任一项即关闭 |

## 三、产品阶段

| 阶段 | 目标与交付 | 放行条件 |
|---|---|---|
| 准备阶段（G0 运营与产品发现） | 将附件每项功能映射到阶段、风险/闸门和责任角色；确认组织、试点社区、A+范围、数据流、渠道与技术约束；用合成案例走查 | 有权负责人签署 G0 发现/授权记录；未决项有责任人和期限 |
| A+ 通用登记与内部分诊 | 可先制作只用合成数据的原型；通用登记入口（居民提交或工作人员代录按 G0 决定）、待判定队列、分诊、转介、责任人、下一步/期限、追加式跟进、撤回/结案/复核、审计 | 原型不连接真实收件渠道。记录先进入内部分诊，不自动公开或派单；真实数据启用前，按 R×G 矩阵满足适用的 G1/G2/G3，并有明确签署人、字段/留存和在岗值守 |
| B1 获批服务履约 | A+有限真实试点复盘后，若运营方单独批准软件立项，再开发实名用户发布获批类别求助订单、任务接单大厅、志愿者接单/取消、到达/签到、完成确认、服务时长记录/确认、评价、事务通知和争议/投诉转人工 | A+试点复盘后单独作出 B1软件开发 go/no-go；求助订单发布前强制实名，首发服务逐类获批，容量与人员/值守明确。B1软件验收与真实上线授权分开；上线前重新通过适用的 G1/G2/G3。B1记录双方确认的实际服务分钟数；争议转人工。计量、修约、取消/部分履约等规则由运营方确定，不自行推导。B4再启用账户余额、流水与兑换。运营方如要求工作人员审核/协调，应纳入大厅内获批流程；若改为定向派单，作为正式需求变更记录 |
| B2 首页/社区/内容运营 | 首页发现、公告与知识、邻里动态、志愿日记、活动、评论互动、附近发现、群入口、闲置互助和内容管理 | 各功能独立开关；审核、举报/屏蔽、撤回、位置/图片处理与支持人员就绪 |
| B3 消息/个人服务 | B3a 系统/个人中心能力；B3b 用户间私聊（单独开关）。B1所需身份与事务通知须作为 B1 依赖先行交付，不等待整个 B3 | 事务通知失败进入人工待办；私聊具备举报、屏蔽、访问审计、留存/导出和支持责任 |
| B4 时长与兑换 | 余额/逐笔流水、服务兑换、核销、排行榜、证明 | 时间规则、对账、冲正、退出与争议责任获批；兑换供给及服务逐类获批。不得自行推定时长到期、转移、现金折算或其他账户规则 |
| B5 高风险服务 | 陪诊、涉儿童/接送、上门、健康字段；附件明确要求紧急入口一键呼叫社区管理员及附近志愿者，并向管理员推送通知 | 上述呼叫与推送是需求，不是已获准的运营承诺。逐项完成责任、人员条件、保护、值守、升级/停用和数据评审并取得 G3 授权；平台呼叫/推送默认关闭，启用前需明确合作方、实时值守、备援、送达监控和演练；否则不开放平台紧急受理，只提供核验过的外部渠道，不承诺平台自动响应 |
| B6 稳定与扩展 | 多社区隔离/移交、运营报表、恢复与长期维护 | 单社区运行指标达标，维护责任和预算明确 |

“我的”具体功能需产品发现确认；附件仅确认该入口及参考图上的部分服务时长能力。附件图片中的时长数字、排行、场景和服务图示均是需求/视觉线索，不是当前运营承诺或真实数据。

## 四、A+ 个案生命周期、SLA 与异常流程

以下是供 G0 确认的 A+内部收件/分诊状态机草案，不代表已获准处理真实个案。A+只跟踪受理与分诊，不跟踪志愿者履约完成。每次状态变更要记录操作者、时间、来源、前后状态、原因；对外通知仅在渠道和内容获批后发送，并记录发送结果。

| 状态 | 进入条件/主要责任人 | 下一步 |
|---|---|---|
| 已收件 | 工作人员从获批渠道录入 | 初筛；有即时危险线索则停止普通流程并升级 |
| 初筛中 | 登记/分诊负责人接手 | 待补充、已受理待分诊、转介、拒绝或撤回 |
| 待补充 | 仅在确有必要且运营方批准联系时使用 | 收到补充后回到初筛；超时只触发内部 SLA 待办 |
| 已受理待分诊 | 运营方确认属于登记范围 | 进入获授权人员分诊，不等于有容量或已承诺服务 |
| 已转介（待确认/已接收） | 授权人员记录转介目标与状态 | 跟进转介结果；转介不等于服务完成 |
| 已拒绝/已撤回/已关闭（未提供服务）/已提供信息 | 有权限的人记录结果、原因及下一步 | 终态；重开时关联原记录并保留历史 |

B1履约另用独立状态：`已发布任务 → 待接单 → 已接单 → 已签到/服务中 → 待确认 → 已完成 / 争议 / 取消 / 转介 / 无人承接`。求助订单发布前实名；任务大厅是附件默认需求。A+的“已收件/已受理”不能显示为“已发布/可接单”，A+转介也不等于服务完成。定向派单替代任务大厅须由运营方批准并记录正式范围变更。

超时是 SLA 标记和内部队列，不是个案状态，也不自动触发外联、关闭或视为已解决。请求人撤回请求是业务事件；撤回/变更数据处理同意是独立的隐私事件，两者均记审计。后者触发停止非必要处理并按运营方批准的留存/删除规则处置，保留所需的最少审计记录。

异常必须有明确路径：重复来件建立关联并由授权人员决定合并，不静默覆盖；无法联系由人工决定是否继续、转介或关闭；转介失败回到责任队列；投诉进入独立复核；工作人员离岗时批量重指派并记录原/新负责人；系统不可用时启用人工登记和恢复后补录；重开建立关联记录，不抹除旧历史。每个未结事项都需有负责人、下一步和经 G0 批准的时限。

即时危险、儿童保护、医疗、入户或疑似伤害线索在所有阶段均触发停止普通分诊并升级给指定负责人；不自动派发志愿者，也不承诺平台紧急响应。紧急信息由指定人员定期核验；无法保证准确性时不展示。精确住址、健康细节、儿童信息、图片和位置默认不纳入 A+。

对儿童、脆弱成年人、入户或身体照护等场景，G1须形成单独的保护规则。人员核验、监护人同意、双人/陪同机制、避免未受监督的一对一私聊、保险和事故报告等作为风险评估候选控制，由运营方和相关专业人员按场景确认；缺少可执行保护/升级方案时 R3 不放行。

## 五、B 主流程与验收

对获批服务走通：实名认证 → 居民发布求助订单 → 提交后进入任务接单大厅 → 合格志愿者接单或取消 → 到达/签到 → 按服务 SOP 完成确认 → 事务通知及投诉/争议闭环。运营方如要求工作人员审核/协调，应纳入大厅内获批流程，不改变订单提交后进入任务大厅的产品要求。B1先具备身份与事务通知（成功/失败状态可追踪），B3后续再扩展通用消息和个人中心；失败通知进入人工待办。B4通过前不将完成记录换算为可兑余额。任何服务都不能仅凭附件列出自动开放。

### B1 后续实施验收基线（当前不实施）

以下矩阵保留为未来 B1 的产品验收基线，不表示当前原型包含这些流程。只有完成有限 A+真实人工试点并复盘后，运营方依据证据单独批准 B1 软件立项，才重新估算并实施。届时可用合成数据验证实名门槛、任务大厅、接单/签到/完成、时长确认、通知失败待办和投诉闭环；不得以当前 A+ 原型或 A+试点替代 B1 验收。B1开发批准不等于 B1真实服务上线批准。

| 环节 | 建议默认规则 | 可验收结果 |
|---|---|---|
| 实名 | 先确认目标小程序平台是否提供可用核验能力；优先只保存核验状态及供应方引用，不在业务库保存证件影像。G0/G1确定核验主体、失败申诉、访问范围和留存 | 未验证账号提交订单被阻止；验证成功后可提交；后台只显示授权人员需要的核验状态；失败原因可申诉并留审计 |
| 地点 | 发布时先收社区及粗略服务片区；精确地址非必填且不进入公开大厅。只有接单后确有需要、用户同意并符合服务规则时，才向该订单的获授权志愿者披露 | 未接单志愿者和公开页面看不到精确地址；获授权接单者按规则获得必要地点；访问留审计 |
| 任务大厅可见性 | 默认在实名、必填字段、服务白名单和容量规则通过后立即对获授权志愿者可见。工作人员在大厅内协调；如要先隐藏待审，须由运营方书面选择为正式流程并界定时限、可见对象和申诉/通知 | 合格订单提交后出现在大厅；被隐藏/下架须有权限、原因、操作者、时间和后续通知记录 |
| 志愿者资格与评价 | 各服务类别由运营方定义最低资格/培训条件；B1首期只开放已核准类别。评价支持投诉/复核，避免公开个人评价造成报复或泄露 | 不符合白名单的志愿者不能接单；评价可撤回/申诉/复核，投诉与被投诉履约人分开处理 |

### 基础易用性与弱网默认

- 表单使用清楚直白的中文、可放大文字、足够点击区域和不只靠颜色表达的状态；遵循目标小程序平台可用的辅助功能能力。
- 弱网时明确显示提交状态，允许安全重试且避免重复建单；敏感字段不默认长期保存在未受保护的本地草稿中。
- A+默认不收图片；后续获批图片上传前去除 EXIF/位置等元数据，并限制公开显示、下载和保留期限。

### 试点最低安全验收

真实数据或真实履约开放前，至少验证：工作人员多因素认证、最小权限角色、传输与存储加密、不可静默修改的关键操作审计、开发/生产数据隔离、备份恢复演练、授权数据导出/删除流程、事故上报与停单手册。由运营方及数据/系统负责人确定适用环境、责任人和验收证据。

“发布”页保留三条独立路径：①求助订单，需实名并进入任务大厅；②志愿服务日记，图片、匿名和分享到社区均为可选项；③普通邻里动态面向社区发布，不是服务订单、不产生服务时长。消息页保留系统/订单通知、私聊、投诉反馈；私聊含文字/图片/位置能力并单独治理，投诉需由管理员处理并推送结果。附件里的“我的”入口及服务时长账户/兑换图示按对应 B4范围处理，不扩展推断其他功能。

当前 A+ 本地原型只用合成数据检查收件、初筛/分诊、跟进、转介演练、结案和高风险停止提示。B1 的实名拦截、入厅、接单/签到/完成/时长确认、无人承接、通知失败、履约争议等场景保留为后续合成验收；须在 A+试点复盘后另行批准 B1开发，不能由 G0/G1直接触发。B1生产上线还需单独批准。撤回、超容量、服务中断、错记账、批量改派、系统恢复和重开按适用闸门分别验收。紧急入口默认只提供经核验的外部渠道与人工升级说明；一键平台调度需合作方、实时值守、备用方案、演练及单独批准，否则不进入排期。

A+真实试点只统计 A+能观测的指标：及时分配责任人的比例、责任人/下一步/期限覆盖率、跟进按期完成率与逾期账龄、转介结果/关闭率、投诉与撤回处理情况。定义、阈值、统计口径和复核人由 G0/G3签署；本地合成原型不能产生或证明运营 KPI。B1接单率/无人承接率、订单通知失败闭环时间和履约争议须等 B1真实启用后另行定义，不混入 A+周报。保护或数据事件作为立即暂停触发器单独记录；无值守、重大事件、未经批准类别开放或超过安全容量时暂停新增。

## 六、开源项目评估与 build-vs-buy

- [Coalesce](https://github.com/FederationOfTech/Coalesce)：README显示志愿者机会、活动招募/签到与报告；没有证明它支持实名求助订单进入任务大厅、志愿者接单/取消/签到/完成确认或争议闭环。需求确认后可对 B1任务大厅和B2活动/志愿者模块分别做 fit-gap；AGPL-3.0，需锁定版本审查。
- [TimeOverflow](https://github.com/coopdevs/timeoverflow)：参考组织/成员角色、供需发布、审核匹配/接单、服务确认、履约记账/争议和线下办公室承接；不照搬其时间币规则。AGPL-3.0；README中的本地 compose 不能视作生产部署验证。
- [CiviCase](https://docs.civicrm.org/user/en/latest/case-management/what-is-civicase/)：CiviCRM中的个案管理组件，作为 A+ 首个 build-vs-buy 基准，评估个案、活动记录、跟进和协调员模型；并非独立轻量收件工具，完整 CiviCRM 可能过重。
- [CaseLight](https://github.com/Lighthouse-Nonprofit/caselight)：作为第二个隔离的合成数据沙箱候选，观察人类服务个案管理字段、角色、表单和审计；先检查部署、访问控制、安全、数据导出/删除、维护和许可，不将其限定为只读，也不接真实数据。
- [Project NEXUS](https://github.com/jasperfordesq-ai/Project-NEXUS)：README声称覆盖较多能力，但成熟度与实际代码未核实，不直接采用。
- 初筛仅查看 GitHub 仓库页/README；没有 clone、运行、依赖、安全或权限审计。因此“尚无已验证直接底座”是初筛假设，不是源码审计后的排除结论。许可证、维护、技术栈契合、部署、备份和升级责任均需在采用前复核。

AGPL 项目在代码复制、修改、组合或网络服务部署前应由项目责任方审查锁定版本与义务，必要时取得法律意见。私有 Git 不自动免除许可证义务。

建议顺序为：先完成附件需求追踪和一页运营模型（个案生命周期、RACI、SLA、字段/留存、异常流程）；再用同一组合成案例，对比 CiviCase、CaseLight隔离沙箱、经核实可用的受控表单/工单、合规 SaaS/低代码和薄型 A+；如 B1/B2运营确有需求，再评估 Coalesce 对任务大厅与活动/志愿者的 fit-gap。试评时长由 G0负责人确认。评分维度包括需求覆盖、生命周期与异常、实名门槛、任务大厅、角色/访问审计、导出/删除、数据控制与部署、许可证/合同、备份恢复、维护责任和迁移成本。评分权重和通过阈值由 G0负责人确认，不预设数值；试评不连接真实收件渠道，也不授权处理真实个案。
