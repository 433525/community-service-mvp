# 离线可用与版本更新（2026-10-23）

本轮目标：让两个入口在**真正断网**时仍可打开、可继续阅读与操作本机数据，并给用户一条明确的「有新版本」通道；同时不破坏既有的首屏体积、视觉与无障碍基线。

范围：只做**前端静态资源**的离线缓存与版本更新，不引入后端、不缓存任何真实数据、不新增第三方依赖（离线环境无法 `npm install`）。

---

## 1. 参考与结论来源

| 主题 | 来源 | 采信结论 |
| --- | --- | --- |
| Service Worker 生命周期 | MDN《Service Worker API》 | 首次访问即下载安装；已有 worker 时新版本停在 waiting，需 `skipWaiting()` + `clients.claim()` 才能立即接管；仅 HTTPS / `localhost` 可用 |
| 更新方式 | vite-plugin-pwa《Prompt for update》 | 默认 prompt 模式不自动接管：弹**非阻断**提示，用户点「更新」才 `SKIP_WAITING` 并刷新；点「稍后」仅关闭提示 |
| 导航超时回退 | Workbox `NetworkFirst` 的 `networkTimeoutSeconds` | 用于对抗 lie-fi（连上 Wi-Fi 但没有出口）：超时先给缓存，网络恢复后仍更新缓存 |
| 预缓存失败语义 | MDN《Cache.addAll()》 | 只要有一个响应非 2xx 就整体 reject，但此前成功的 `put` 会保留 |
| 更新检查时机 | MDN《ServiceWorkerRegistration.update()》 | 主动 `update()` 会重新取脚本；超过 24 小时的获取会绕过浏览器缓存 |
| 分块失败自愈 | Vite《Load Error Handling》 | `vite:preloadError` + HTML `Cache-Control: no-cache`（上一轮已实现） |

**分歧处理**

1. **是否自动接管**：Workbox / vite-plugin-pwa 都提供 `autoUpdate` 一键方案，但本项目是「工作台 + 正在填写的表单」场景，自动刷新会丢输入。按 prompt 模式实现，文档与实现一致。
2. **`Cache.addAll` 还是逐个 `add`**：Workbox 的 `precacheAndRoute` 在任一资源失败时会让整次安装失败。这里对一个**纯静态演示站**选择更宽容的策略：逐个 `add` + 失败跳过，避免某个资源 404 直接把离线能力整体废掉。风险是「部分预缓存」，由门禁 `OF03` 兜底断言清单完整性。
3. **offline 判定的口径**：`navigator.onLine` 只代表网卡链路，无法区分「连着 Wi-Fi 但没有出口」。因此它只用于**提示**，不用于决定是否走网络；真正的容错交给 SW 的 network-first + 3 秒超时。

## 2. 实现结构

| 文件 | 职责 |
| --- | --- |
| `public/sw.js` | Service Worker 本体，构建时注入版本号与预缓存清单 |
| `vite.config.ts` | `offline-sw` 插件：`closeBundle` 阶段读 `dist/`，把 `__SW_BUILD_ID__` / `__SW_PRECACHE__` 替换成真实值 |
| `src/shared/offline-policy.ts` | 纯函数：提示类型判定、更新检查节流、文案（可在 Node 单测） |
| `src/shared/offline.ts` | 状态与副作用：注册 SW、在线状态、waiting 追踪、`SKIP_WAITING`、刷新 |
| `src/shared/components/OfflineNotice.vue` | 两个入口共用的提示条（scoped 样式、`role="status"`、44px 按钮） |
| `tools/check-offline.mjs` | 离线 / 更新专项门禁 21 项 |
| `tools/unit/offline.test.mjs` | 策略纯逻辑单测 11 条 |

### 2.1 缓存策略

| 请求类型 | 策略 | 理由 |
| --- | --- | --- |
| 页面导航（`mode === 'navigate'`） | network-first，3 秒超时回退缓存；成功则回写 | 保证发版后能拿到新 HTML，弱网时不至于白屏 |
| `/assets/*` | cache-first | 文件名含内容哈希，内容不可变 |
| 其他同源 GET | stale-while-revalidate | favicon / robots 之类的小文件，先给旧的再更新 |

缓存键：导航按 **pathname** 归一化（`/` → `/index.html`），因此 `?tab=community`、`?post=` 等深链在离线时同样命中同一份外壳。

### 2.2 版本与更新

- 版本号 = `sha256(两份 HTML + 排序后的资源文件名).slice(0, 12)`，构建时写入 `sw.js`；缓存名 `community-offline-<id>`。
- 内容不变 → 版本不变 → **不会误报更新**；任一资源或页面文案变化 → 新 SW 安装并进入 waiting。
- 首次安装（还没有 active worker）直接 `skipWaiting()`，首访即可离线；升级时停在 waiting，等用户确认。
- `activate` 阶段删除同前缀的旧缓存，只保留当前版本。
- 注册时使用 `updateViaCache: 'none'`；标签页重新可见时按 60 秒节流调用 `registration.update()`，兼顾长驻工作台。

### 2.3 降级

| 场景 | 行为 |
| --- | --- |
| 不支持 Service Worker / 非安全上下文 / 隐私模式 | 注册整体静默失败，页面按普通静态站工作；**不打印 warn/error**，避免把可接受降级误报成页面异常 |
| 用户关掉离线提示 | 本次不再出现，网络恢复后重置 |
| 断网 + 有新版本 | 只提示离线（此时点更新也拉不到资源） |
| 离线访问未缓存路径 | 返回站内兜底页「这一页还没缓存」，而不是浏览器断网错误页 |

## 3. 本轮修掉的两个真实缺陷

### 3.1 `Vary` 导致缓存命中失败（致命）

现象：断网后 HTML 能打开，但 JS/CSS 全部 `net::ERR_FAILED`，页面只剩空壳。

原因：Vite preview 的响应带 `Vary`（含 `Origin`），而预缓存时用 `new Request(url)` 没有附带脚本标签发出的 `Origin` 头。`Cache.match` 默认**参与 Vary 比对**，于是同一 URL 命中失败；随后 `fetch()` 在断网下抛错，`respondWith` 的 Promise reject，浏览器报 `ERR_FAILED`。

修复：所有读取缓存的地方改用 `{ ignoreVary: true }`（资源名带内容哈希，HTML 版本随缓存名变化，忽略 Vary 不会串版本）。

### 3.2 多入口站点不能共用「一个外壳」兜底

现象：离线访问 `/not-cached-page` 时，A+ 工作台里出现了社区端外壳（或反之）。

原因：初版在导航失败时统一回退 `/index.html`。对单入口 SPA 是标准做法，对双入口站点会把用户带到「另一个应用」。

修复：只回退到**该路径自己的缓存副本**；没有就返回站内兜底页。门禁 `OF10` 固定这个行为。

## 4. 门禁设计与一个关键教训

### 4.1 不能用 `Network.emulateNetworkConditions({ offline: true })` 判离线

实测：该 API 只把 `navigator.onLine` 改成 `false`，**对本机回环地址的请求不拦截**——断网状态下 `fetch('/robots.txt?…')` 依然返回 200。用它写断言会得到「假通过」：页面其实一直在走网络。

因此 `tools/check-offline.mjs` 改为：

1. 用空闲端口起一个独立的 `vite preview`（与被测的 5180 互不影响）；
2. 「断网」= **kill 该预览进程**，请求真的被拒绝；
3. 先用 `fetch('http://127.0.0.1:1/probe')` 断言「网络确实不通」，再断言页面仍能渲染；
4. 「恢复网络」= 重新拉起同一端口的预览进程。

同一脚本还会断言「新旧文档已切换」（比较 `performance.timeOrigin`），避免断言打在导航前的旧页面上。

### 4.2 21 项断言

| 编号 | 断言 |
| --- | --- |
| OF01–OF02 | 注册并激活、作用域为站点根、首次安装后当前页面即受控 |
| OF03–OF04 | 16 个预缓存资源全部落盘、版本号与算法一致、无残留占位符 |
| OF05 | 预览已停止，页面侧请求确实失败 |
| OF06–OF07 | 断网后首页完整渲染（外壳/导航/信息流/轮播）、提示条 `role=status`、按钮 44px |
| OF08 | 断网下按需加载的「消息」页签可用 |
| OF09–OF10 | 断网后 A+ 入口可用；未缓存路径给站内兜底页 |
| OF11–OF13 | 恢复网络后提示消失；390px 布局不溢出且避开底栏；过程零异常 |
| OF14–OF15 | 无 Service Worker 时照常渲染、离线提示仍工作、零异常 |
| OF16–OF19 | 新版本停在 waiting、提示可「稍后」、刷新后再次提示、点更新后接管 |
| OF20–OF21 | 新缓存生效、旧缓存清除 |

更新流程的用例会临时改写 `dist/sw.js`（只改版本号）来模拟「发新版」，`finally` 里还原，失败也不会污染产物。

## 7. 未覆盖与风险

1. **真实设备**：iOS Safari（SW 生命周期更激进，7 天未使用可被清理）、微信 X5 内核未实测；本轮仅 headless Chromium 156。
2. **真实弱网**：只做了「完全断网」与「正常网络」两档，没有 3G/高丢包矩阵；3 秒超时阈值是按经验取的，真机需复测。
3. **存储配额**：预缓存约 0.5 MB；隐私模式或配额不足时 `cache.put` 会失败，代码已静默跳过，但离线能力会降级为「部分可用」，门禁不覆盖配额耗尽。
4. **`sw.js` 的 HTTP 缓存**：依赖 `updateViaCache: 'none'` 绕开缓存；若托管方强制给 `.js` 加 `immutable` 长缓存且浏览器忽略该选项，更新检查会退回 24 小时周期。部署时建议对 `/sw.js` 显式设置 `Cache-Control: no-cache`。
5. **未做**：后台同步（Background Sync）、推送、离线写队列；本轮所有写操作本来就是本机 localStorage，不需要服务端同步。
