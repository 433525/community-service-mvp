# 社区服务小程序开源项目初筛

- 日期：2026-10-20
- 目标：面向实际运营，评估整个平台与模块复用，并参考 TimeOverflow 的业务流程。
- 产品基线：用户最新《社区服务小程序功能说明.docx》定义完整目标：首页、社区、发布、消息、我的五栏和运营后台。分期不删减完整目标。
- 首期建议：A+由“通用登记入口 + 工作人员内部分诊队列”组成。登记入口采用居民填写还是工作人员代录、开放范围、渠道和字段，由 G0 运营发现决定；服务类型暂记“待判定/未分类”，由获授权人员后续分类。A+登记不自动发布到任务大厅。B1则须保留附件要求的独立求助订单发布流程：订单发布前实名，获批订单进入任务接单大厅，由志愿者接单/签到/完成确认。
- 证据范围：本轮为官方仓库页、README、官方文档和许可证入口初筛；未克隆、安装、运行或审计代码、依赖、安全、维护和部署。

## 初筛结论

目前没有候选经代码级验证可作为完整五栏平台底座。A+先完成运营模型与合成场景，再以 CiviCase 为首个 build-vs-buy 基准、CaseLight 为隔离合成数据沙箱候选；Coalesce可在需求确认后对 B1任务大厅与B2活动/志愿者管理做 fit-gap，但目前没有证据证明它支持本项目要求的实名求助订单任务流；TimeOverflow用于组织角色和线上线下供需、匹配、服务确认及账务流程参考。项目自述不能证明生产适用性。

## 建议的评估顺序

1. 先完成需求逐项追踪和一页运营模型：服务受理生命周期、RACI、处理时限、允许字段/留存、异常与升级路径。明确 A+ 是通用登记加内部分类跟进；服务类型可以后定。
2. 编写同一组合成案例，覆盖 A+ 新登记/未分类/补充/转介/拒绝/重复/失联/投诉/撤回/超时/重开/交接，也覆盖 B1订单实名门槛、任务大厅发布、接单/取消/签到/完成确认、争议和服务停用。
3. A+以 CiviCase 为第一基准，CaseLight 作隔离的合成数据沙箱候选；Coalesce在 B1任务大厅和 B2活动/志愿者方面分别做 fit-gap。检查现成服务台/低代码方案时，先核实数据控制、合同、导出删除、权限审计和退出能力，再与薄型 A+ 原型比较。
4. 评分至少覆盖流程适配、角色/审计、数据导出迁移、部署恢复、维护责任、许可/合同和试点成本；试评时长、评分权重和通过标准均由责任人确认，不预设数值门槛。
5. 即使配置试评通过，也只决定技术候选，不授权接入真实居民数据或开放真实履约。真实运行需另外通过适用治理闸门。

## 产品阶段映射

- **A+：**通用登记入口、内部分诊与跟进。CiviCase优先作 build-vs-buy 基准，CaseLight作为隔离合成数据沙箱候选。不得自动公开到任务大厅或派单。
- **B1：**服务白名单获批后，求助订单发布前实名，并进入附件要求的任务接单大厅；评估审核、接单/取消、到达/签到、完成确认、通知、争议和投诉闭环。Coalesce仅做任务流 fit-gap，不假设活动模块即满足任务大厅需求。
- **B2：**Coalesce可在活动/志愿者管理成为实际运营需求后单独复评；活动招募与服务求助任务分开评估。
- **B3：**事务通知、一般消息、私聊分开评估；不能因开源项目有“消息”页面就推断举报/屏蔽等治理足够。
- **B4：**TimeOverflow用于角色与线上线下时间银行流程参考；本项目规则需由运营主体另行决定。
- **B5：**儿童、医疗、紧急、入户等类别按场景批准和配置保护；代码复用不能替代运营责任。
